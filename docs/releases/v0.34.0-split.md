  Help/schema／synthetic PASS 不代表 live lifecycle 或 OS 隔離；#242／#251／#293

已觀察 main `0bcc1568…` 的 [controller run 39040871501](https://github.com/jeffery777/codex-dev-skills/actions/runs/39040871501)

### 安裝、更新與回復前提

本階段完成發行後先交接，不直接修改用戶安裝。以下程序須在正式 Codex tag／
Release 身分與完整 gates 核對、且實際 targets／資料保護計畫確認後執行。

1. 維護者讀回 Codex annotated tag object、dereferenced commit、正式非 draft／
   非 prerelease Release target，並核對其 bundled Core 正式 tag／commit、三種固定集合
   digest、最終核對的完整 13 檔 inventory／bytes／modes 與 notices。
   兩者一致且適用 gates 完成才選安裝來源。
2. 使用完整、明確 origin 的本機 Git checkout；固定 HEAD，核對 catalog 與完整 payload。
   ZIP／partial／promisor checkout 不是 filesystem installer 的受支援來源。
   選目前受審 installer 程式及受支援 `--source` payload；舊來源只當資料，不執行舊 installer。
3. 準備 Bash、Git 與 Python 3 標準函式庫。Repository 驗證另需 tracked Python
   3.12.9／PyYAML；選定技能的既有相依另核對。受限 memory-maintenance 的隔離
   Python／SQLite runtime 不會由安裝技能自動建立或啟用。
4. 每個 Codex profile 選 filesystem 或窄 plugin 一種 distribution，先盤點
   `~/.agents/skills`、legacy／imported／plugin copies、templates、profiles、state
   與明選 custom targets，防止重複 selectors。保留使用者自訂檔及歷史 recovery。
5. 新 receipt 安裝先查 `status`／`diff`，確認完整 roots tuple 與所有管理群組。
   不同 catalog 的換版（含相同版本號）明選 `--all`；不新加入 profiles，已管理 profiles 仍更新。
   記錄原固定來源身分與取得方式；需要離線回復時才預先準備來源。Cache 可選，
   不要求永久保留完整 checkout／整包備份；source 不可取得就不能承諾離線重建。
6. 舊 receipt 或沒有可驗管理權時停止 mutation。Agent 逐一盤點 target ownership、
   自訂 bytes／modes／未知內容與可回復來源，提出確切換版方案，取得適用操作確認。
   不用 `--force`、刪 receipt、同 bytes 或舊 source commit 代替管理權證據。
7. 完成實際操作後獨立讀回完整 payload／Core／receipt／退休檔，檢查 cleanup pending，
   再開新 session。Plugin 使用公開安裝／更新流程與實際來源讀回；不套用 filesystem
   receipt 成功結論，也不混裝。Profiles 是另行 opt-in，不改目前主代理設定。

正式 fixed-source 操作形式如下；路徑須先由上列程序核對，這些例子不授權執行：

```sh
/trusted/current-program/install.sh install codex-review-workflow --source /trusted/fixed-payload
/trusted/current-program/install.sh update --all --source /trusted/fixed-payload
```

降版仍用目前受審程式，將 `--source` 改選受支援的原固定 payload。完整交易成功後
才能視為回復。本版預定支援 0.33.1、原 Core PR #16 的開發版 0.34 與正式 Core
v0.1.0 的 split 0.34 三份固定 payload。後兩者版本相同而 catalog 身分不同，更新
仍須明選全部管理群組；舊 receipt 辨識、profiles 保留、Core root 升降／回復及部分
uninstall 均須本案完整驗收。一般 loader 僅接受正式 pin；installer 以明選的靜態
歷史 allowlist 重建舊資料，不執行舊 validator，不接受任意鎖內 hash。
交易成功後只清理本次可重建 originals；歷史 backups／未知檔／回復失敗原件保留。
遇非零、`CRITICAL` 或 cleanup pending，保留輸出的精確 recovery 位置，先查哪一步
完成，再由操作人員決定確切回復。無 SIGKILL／斷電跨根原子性、敵對 same-UID 隔離
或跨 state namespace 互斥保證。細節見[固定來源安裝與回復](../installer-source-integrity.md)。

### Installation, update and recovery prerequisites

This release stage does not change user installations. Apply this procedure only
after verifying formal Codex publication, gates, actual targets and data protection:

1. Read back the annotated Codex tag, dereferenced commit and non-draft,
   non-prerelease Release target. Verify the bundled formal Core tag/commit,
   all three set digests, the final verified complete inventory's bodies/modes
   (the thirteen-file formal closure) and notices.
2. Use a complete local Git checkout with the expected origin and fixed HEAD.
   ZIP, partial and promisor checkouts are not supported filesystem sources.
   Run the current reviewed installer and select a supported `--source`
   payload; never execute an old source's installer.
3. Provide Bash, Git and Python 3's standard library. Repository checks use
   pinned Python 3.12.9 and PyYAML. Check each selected workflow's dependencies.
   Skill installation does not create or enable the isolated memory runtime.
4. Choose one distribution per Codex profile. Inventory standard, legacy,
   imported, plugin, template, profile, state and custom roots. Avoid duplicate
   selectors; preserve custom files and historical recovery data.
5. For receipt-managed installations, inspect status/diff and the full roots
   tuple. Cross-catalog replacements, including the same version, select all managed groups with `--all`.
   This does not add profiles, but retains/updates managed profiles.
   Record the original fixed-source identity and retrieval method. Prepare a
   local source in advance only when offline recovery is required. A cache is
   optional; no permanent full checkout or package backup is required. Offline
   reconstruction is unavailable when the source cannot be obtained.
6. Stop when ownership cannot be verified. An Agent must inspect legacy
   ownership, custom content/modes, unknown files and recoverable sources,
   then obtain the applicable approval for an exact replacement plan.
   Force, deleted receipts, equal bytes or an old revision cannot prove ownership.
7. After an authorized operation, independently read back payload, Core,
   receipts, retired-file absence and cleanup state. Start a new session.
   Use the plugin's public lifecycle and source readback separately; filesystem
   receipts do not qualify it. Profiles remain a separate opt-in and do not
   change the active main-agent configuration.

The command forms above are examples, not execution authority. Downgrades use
the current reviewed program with the supported older fixed payload.
Only a complete successful transaction establishes recovery. The intended fixed
sources are 0.33.1, the PR #16 development 0.34 snapshot and the formal-Core split 0.34
snapshot. Equal version strings do not imply equal catalogs; select all managed
groups for replacement. This issue must verify old receipt recognition, retained
profiles, root-level Core transitions/recovery and partial uninstall. Ordinary
loading accepts only the formal pin. The current installer explicitly validates
the fixed reviewed history; it never executes an old validator or trusts arbitrary
lock hashes.
Success removes only this transaction's verified reconstructible originals.
Historical backups, unknown data and failed recovery originals remain.
On failure, preserve exact recovery paths and inspect completed steps before
an operator selects recovery. SIGKILL/power-loss atomicity across roots,
hostile same-UID isolation and cross-state locking are not guaranteed.
See the fixed-source guide linked above.
