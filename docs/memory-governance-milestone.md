已驗證基準為 Git `53a60a000ec6bcdf78a31aa96dc4c1479d78b8c2`；
規劃開始時 HEAD、本機 main 與本機 origin/main 一致。這不是即時遠端證明。

內容清除與磁碟回收仍是缺口。既有 M1 的技術 `delete` 是 logical delete，
不能因新產品需求而偷偷改義。新設計需要版本化儲存及操作契約，
相關差異集中於技術附錄；舊契約不是新產品能力的永久上限。

本階段只更新 roadmap、此規格與研究文件。保留現行 catalog、既有發行紀錄、
技能及程式；不讀取真實記憶、Desktop 私有資料、log、session、cache、

若發版評估成立，先提出具體版本、候選變更與驗證計畫供核准，再於 #212
追蹤發行準備；本階段尚未變更版本或授權發布。

## 建議架構與取捨

建議兩個自然語言入口，共用一個本機管理核心：

- `memory-audit`：取得盤點與容量資料、比對來源、提出人類可讀的建議。
- `memory-maintenance`：解析人類要求、顯示精確預覽、驗證確認、執行及回報。
- 共用核心負責範圍、內容版本、目前使用狀態、操作紀錄、刪除及容量統計。
  只有 maintenance 能進入變更路徑；文字建議本身不能啟動操作。

評估選項：

| 選項 | 優點 | 本專案判斷 |
| --- | --- | --- |
| 一個 skill 以明確讀／寫模式運作 | 安裝表面最少，共用流程容易 | 可行，但盤點入口較易意外取得寫入路徑；暫不優先。 |
| 兩個薄 skill＋共用本機核心 | 沿用本 repo 審查／變更分離模式，避免複製解析與契約 | 建議採用；實際寫入權限仍由核心及 runtime 驗證，skill 名稱不是安全隔離。 |
| 直接導入 Mem0 或 Zep 等 backend | 現成管理介面與檢索功能 | 保留為另案比較；本次需求不需要外部模型、向量服務或圖資料庫，且供應者行為尚未通過本專案資格驗證。 |
| 完全沿用 M1 且只增加提示詞 | 初期工作最少 | 無法完成可靠盤點、修改歷史與清除；不採用。 |

借鑑 Mem0 的明確管理操作與歷史介面、Zep 的時間及來源關係、
Letta 的使用關係／管理能力分離；再借鑑 Memora 的內容／檢索表示分離，
以及 PlugMem 將經驗整理為事實與可重用方法的思路。
採本機單一交易儲存，以減少跨服務一致性問題。
這是基於本專案需求的設計判斷，不是宣稱其他產品較差或已替本專案通過測試。
M2 原本保留給第二供應者／MCP，這項治理工作暫稱 MG1，避免混淆。

### 微軟研究對提案的補充

Memora 與 PlugMem 的定位、固定原始碼版本及缺口見研究文件。
以下是適合本專案的調整，不是安裝它們或移植其自動記憶流程：

- 將「主題／短摘要」「實際保存內容」「檢索線索」分開表示。
  摘要供盤點與定位，不能取代確切內容、條件、數字、例外及來源。
  G0 定義它們的格式與 byte／數量上限；首版可用 FTS 與有限關鍵詞，
  不加入 embedding、共用 cue 圖、額外模型服務或強化學習。
- 事實型內容說明「目前知道什麼」；方法型內容包含適用前提、步驟、
  成功證據與失效條件。這是人類可讀的分類提案，不改既有 record enum。
  完整 session／原始事件並非預設保存單位，不為重用經驗而存進私人聊天或 log。
- 同一已確認項目的更正使用新 revision；相似度、重複查詢、使用者糾正或
  一次成功只能形成候選，不能證明兩項是同一事實或取得寫入權限。
  首版不新增跨多筆的自動 merge；需要整理多筆時，仍各自走精確操作確認。
- 主題與線索綁定同一 scope、memory identity 及 revision，不能把自然語言標籤
  當唯一身分或存取權。舊線索隨版本切換退出一般 recall，刪除時一併清理。
  新內容、摘要與線索先準備及驗證，再同交易切換；不先刪舊內容再等待模型輸出。
- 檢索可先看有界目錄／摘要，再讀必要內容與來源；列舉完整性與內容查核覆蓋率
  分開回報。需要擴展查找時仍受原讀取範圍、步數及輸出預算限制，
  不從記憶文字取得新權限，也不因結果不足就啟用另一個外部 backend。

PlugMem 的方法型記憶仍只是本專案的 advisory data，不自動成為
`AGENTS.md`、`SKILL.md` 或新的執行規則；提升為正式技能／規則須經既有
獨立變更與審查。整理與壓縮不得丟失反例或把曾經成功誤寫為永遠適用。
本輪不放寬既有 PlugMem／Mem0 backend 排除條款，不新增 hooks、服務或自動採集。

## 人類看到的操作

主要報告、確認文字與操作名稱使用普通語言。工程識別碼、雜湊、資料表及
格式版本只放技術附錄／機器介面。使用者不必建立或執行底層命令。

| 人類要求 | 提議的效果 | 復原與空間影響 |
| --- | --- | --- |
| 「盤點這個專案的記憶」 | 列出範圍、內容狀況與容量，提出建議 | 不改動持久資料。 |
| 「記住這項決定」 | 保存通過來源驗證的新內容 | 增加空間；之後可停止使用或刪除。 |
| 「把這項決定改成……」 | 同一項記憶更新為新版本，舊版不再供一般回想使用 | 保留有限的可回復版本，不能永久累積全文。 |
| 「不要再用這一條」 | 停止回想，內容仍在 | 可重新驗證後恢復使用；不聲稱節省內容空間。 |
| 「恢復使用這一條／改回先前版本」 | 重新驗證範圍與來源後恢復，留下新操作紀錄 | 不可恢復已清除內容，也不會把舊的錯誤決定自動變回有效。 |
| 「刪除這一條」 | 預覽從受管理儲存移除該項及其舊版內容；確認後清除 | 完成後本系統無法復原，保留的刪除證明不含原文。 |
| 「整理資料庫空間」 | 回收已刪除資料留下的空白，不選擇哪些記憶該刪 | 另顯示預估與實際空間、鎖定時間及暫存需求。 |

「刪除」預設呈現內容清除的效果與範圍。若人只想暫時不用，提供停止使用的選項。
遇到「忘掉它」等模糊用語，先釐清這兩種效果，不自行選擇不可復原的動作。
使用舊 M1 時必須說明「目前只能停止使用，內容仍保留」，不能執行舊
logical delete 後回覆「已永久刪除」。

不強制每次刪除先進垃圾桶或先備份。那會使「已刪除」仍保存原文。
想要可逆時採停止使用；真的刪除時明確確認不可復原。
若未來另提供延後清除，必須顯示實際保留期限與尚未清除狀態。

## 盤點分類、證據與信心

盤點結果供人決策，不是自動清理指令。每筆採一個主要分類，可有多個原因：

| 類別 | 需要的判斷與證據 |
| --- | --- |
| 可繼續使用 | 目前可驗證的來源支持其內容與適用範圍。 |
| 建議修改 | 找到明確更正或新資訊；並列舊說法、新說法與來源。 |
| 建議停止使用 | 與現行規則衝突、被替代或範圍已改變，說明受影響情境。 |
| 需要人確認 | 來源不足、互相矛盾、無法判斷是否仍有價值，列出缺失。 |
| 已停止使用／已被替代 | 說明保留理由、可復原性、可評估清除的舊版容量。 |
| 疑似不應保存 | 只顯示遮蔽後的識別資料與問題類型；建議人類處理。 |

時間久、使用少、檢索排名低及容量偏高，只能影響盤點順序。
不得僅憑這些訊號建議刪掉有效記憶，更不得直接清除。
「來源不可信」「已被取代」也必須有可追查證據及人類決定。
內容具有保留價值與是否值得保留舊版本，是不同判斷。

每筆顯示安全摘要、穩定標籤、範圍、來源與驗證時間、判斷理由、
信心（高／中／低）、誤判或刪錯的影響，以及「什麼新證據會改變結論」。
高信心須有目前獨立來源與一致範圍；部分佐證為中；
只有記憶自述、失去來源或矛盾未解為低。沒有校準資料就不顯示精確百分比。
刪錯風險分開說明：是否唯一來源、是否仍有依賴、能否復原，
不能用高信心抵銷不可復原性。沒有使用統計時顯示「未知」，不得捏造低使用量。

原始盤點由底層先驗證並遮蔽疑似禁止內容，再交給語言模型。
可疑原文不得進入工具輸出或報告；秘密的短雜湊也不能當安全摘要。
偵測仍不是完整的資料防洩漏保證；無法安全處理時停止該內容的採用。
資料缺失不等於應刪除，單筆未知也不得影響其他已驗證項目。

## 預覽、確認與變更紀錄

盤點須有明確的讀取範圍，不搜尋家目錄或擴大到其他專案。
盤點結果不完整、翻頁期間內容改變、超出上限或來源失聯時，
顯示涵蓋範圍與限制，不能說「全部正常」。

新增／修改顯示通過敏感性檢查後「實際將保存的完整內容」，不是只有摘要。
停止使用／刪除顯示可辨認的項目、來源、適用範圍、受影響版本與衍生內容、
是否可復原及容量影響。預覽同時說明保留哪些操作證明、有哪些副本不在控制內。
文字與執行目標須由同一份結構化預覽產生；機器端綁定完整內容與精確目標。

建議所有變更均在預覽後取得一次明確確認；已確認相同預覽時不重複詢問。
目標、內容、來源證據、範圍、狀態或期限改變就重做預覽。
自然語言處理只能形成候選，不能自行產生可信授權。
使用者可直接要求 maintenance；不必先跑 audit，也不必知道 skill 名稱。
批次及萬用字元刪除暫不納入；單一項目之全部版本為一個可預覽的影響集合。

歷史區分「可回復的舊內容」與「已發生的操作證明」。
後者只記範圍、操作與不透明識別、時間、確認／證據的受控引用、
前後版本或狀態及結果，不複製聊天、預覽全文、秘密或舊內容。
新增、修改及刪除的成功紀錄與資料變更同一交易提交。
驗證失敗與取消在當次回應呈現；不為每次拒絕另寫一套 audit log。

既有 M1 操作紀錄只能如實投影，不能宣稱它保存了完整使用者意圖或身分證明。
新版本須另定操作紀錄的授權與保留規則；歷史只證明受限範圍的執行，
不替代獨立的權限、來源、驗證或完成判定。

## 刪除內容與回收容量

本設計分別回報三件事：

1. 是否還會被使用：停止使用即可阻止回想，但原文仍存在。
2. 受管理內容是否移除：包含目前版本、舊版、內容索引及管理核心保存的衍生副本。
3. 磁碟是否回收：移除資料後的空白可再利用；檔案是否縮小須另量測。

[SQLite 官方說明](https://www.sqlite.org/lang_vacuum.html)指出刪除後的空白頁
通常留在檔案內，重整可回收空間且需要額外工作空間。因此不能把
「檔案尚未縮小」誤判為刪除未生效，也不能把停止使用當作空間回收。

內容清除必須列出版本、索引、歷史全文、暫存／復原檔及受管理副本的關係。
有共用衍生內容時，先重建成不含該來源的版本，或停止採用並要求人類決定；
不得為刪一條記憶毀掉其他來源支持的資料。首版不建立跨多筆共用圖或
模型綜合摘要；單筆主題／摘要／線索則是同 revision 的受管理衍生物，
與正文一同納入清除。只管理明確可追蹤的記錄與索引，讓完整清除有界。

刪除證明不保存被刪原文或可還原全文的差異。
已經交付給先前對話、使用者匯出、舊 M1 儲存或外部備份的副本，
必須標明不在本次清除範圍；不能擅自讀取或清除它們。
若使用者要求連這些副本一起刪除，另列精確範圍，未完成前不得聲稱全部清除。
SSD、作業系統快照與取證級抹除不在本機管理 API 的保證內。

容量報告至少分出使用中內容、停止使用內容、舊版全文、操作證明、
索引／資料庫額外空間、可再利用空白、檔案實際大小與維護工作空間。
各估算標明不可直接相加的項目，不以全文字數假裝磁碟實測值。

保留策略建議：

- 有效內容沒有以時間或使用頻率觸發的自動淘汰。
- 舊版全文採「最多 10 版／30 日」作待校準的盤點門檻；超過只提出
  精確清除清單，需確認才移除。這是提議值，不是產品既有預設。
- 操作證明與防重放資料也必須有容量與保留界限；不能無限增長。
  淘汰它們前須先證明過去請求再送入時只會拒絕，不會重建已刪內容。
- 建議 80% 預警，新增與修改必須留出已量測的交易／維護預留空間。
  達上限時停止增加資料；保留讀取及經資格驗證的清除路徑。
  真正磁碟已滿時可能連刪除都需工作空間，必須如實報告。
- 空間重整是手動明確操作，不能只因時間到或容量高就刪記憶。
  拒絕清理時持續可讀但可能無法新增，不能承諾有限容量內無限寫入。

## 交付範圍、階段與 DoD

實作前先接受本方案，再進行以下可獨立審查的工作包。
G1 可先交付部分能力，但不得把 G1 描述為完整治理里程碑。
依賴順序為 G0 契約接受後才開始 G1；G2 依賴 G1 的版本、索引與操作紀錄，
G3 整合 G1／G2 的驗證證據。安全與故障測試隨各階段交付，不能全部延至 G3。
下一個最小工作包是 G0 的契約與合成案例，不是直接實作清除；須先另建
Issue，再依其 ID 建立分支，不在 #212 混入新資料契約或執行核心。

| 階段 | 必要交付 | 達成條件 |
| --- | --- | --- |
| G0 契約與合成資料 | 範圍／預覽／授權、版本資料、刪除集合、保留與防重放設計 | 具體格式、時間／容量上限、失敗模型及安全審查完成。 |
| G1 盤點與日常維護 | 兩入口、完整有界盤點、新增／修改／停止／恢復、有限歷史 | 任一新舊關鍵詞都不能召回已被替代版本；修改及證明一致。 |
| G2 內容清除與容量管理 | 真正移除全文及衍生內容、容量計量、手動重整、狀態復原 | 刪除後已覆蓋的讀取與歷史路徑均無原文，容量可回收，重試不復活。 |
| G3 資格驗證與文件 | 故障注入、隱私、相容性、包裝、使用說明與正式審查 | 完整目標具證據，版本／發行另行決定。 |

本階段不修改任何技能、腳本、adapter 或資料庫。未來方案仍維持
default-off、local/manual/CI、single-host、無背景服務；
不增加自動回想／寫入、MCP／外部 provider、向量模型或資料圖，
不承諾共享主機機密性、加密、未驗證的效率改善或產品記憶遷移。

完整 DoD：

- 一般人能以自然語言完成五種核心要求；讀取與變更路徑清楚且驗證權限一致。
- 盤點有完整性與來源證據，狀態及風險自然可讀，工程詞不進主要文案。
- 語意分類、資訊替代、適用範圍與禁止內容只產生有證據的建議；
  舊或少用不會讓 agent 自行刪除。
- 新增／修改與目前來源、驗證及審查證據一致，缺少資格時只留未保存提案。
- 修改、停止及恢復不誤動其他範圍；舊版不會因不同搜尋詞重新生效。
- 刪除包含同一項目全部內容版本及已列明衍生物，保留證明不含全文；
  不能用停止使用、查詢無結果或 HTTP 成功回覆充當完整清除證據。
- 清除重試、資料庫重開與舊請求重播均不復活已刪內容；已清除的歷史不假裝可復原。
- 量測資料庫、空白頁、操作證明與維護空間；循環新增／修改／清除能在固定預算內持續。
  若沒有清理授權，達上限安全拒絕寫入。
- 更新／清除／重整各有可區分的狀態、故障復原及獨立成功判定。

## 技術附錄：現行契約與新核心

### 已驗證來源及差距

- [V2b](external-memory-contract.md)、
  [portable reference](../skills/loop-engineering/references/memory-contract-v1.md)：
  記憶為不可信 advisory data，來源、範圍、敏感性、eligibility 與外部 accepted evidence 分離。
- [M0](memory-operation-contract.md)及
  [reference](../skills/loop-engineering/references/memory-operation-v0.md)：
  精確操作、trusted time、idempotency、atomic receipt；`delete` 只有 logical-delete。
- [M1](memory-sqlite-reference-contract.md)及
  [reference](../skills/loop-engineering/references/memory-sqlite-v0.md)：
  固定 schema、scope isolation、64 MiB database bound、FTS5 probe；
  不支援 purge／migration／repair／backup／restore／vacuum。
- [qualification](memory-qualification-contract.md)與
  [loop entry](../skills/loop-engineering/SKILL.md)：
  memory-off zero-touch，結果不授權 activation／promotion／completion。
- 現行 `memory_sqlite.py` 的同 ID upsert 覆寫 record JSON；
  新 ID 的 supersedes 只有同時出現在回應時才能在 V2b 壓過舊版。
  search 不是完整 inventory；舊 operations 也不保存所有失敗或使用者原話。

### 版本模型與相容性決策

建議新版本在同一 SQLite 交易域內管理 current pointer、immutable content revisions、
FTS 索引及 bounded operation receipts。這是資料模型提案，不是已存在表名。
對外保有一個穩定 memory identity；修改產生新 revision，原子切換 current pointer、
索引及 receipt。一般 recall 只讀目前可用 revision，歷史須走明確 read scope。

新核心為這些語意定義版本化 operation／storage contract，並重新資格驗證。
重用 V2b 的驗證與 advisory 邊界；可輸出合規 canonical records，但不可在
`loop-memory/v1`、M0 v0、M1 v0 的既有 enum／extension 偷塞新 shared 語意。
`update`／`restore`／`erase-content`／`compact` 是待定新機器操作；
現行 `delete` 仍是原語意。

首次資格驗證採合成資料的獨立、明確核准 state root，不自動遷移舊 M1。
既有資料留在舊界面；跨版本搬移須另定匯入、來源與舊副本處置契約。
若新 schema 無法在不遷移既有庫的方式部署，回到 G0 調整，不默默更新舊庫。
G0 必須規定防止同一 logical identity 跨新舊 root 被誤當同一刪除目標。

### 授權、歷史與防重放

授權一次綁定精確 scope、state root、revision/pre-state、candidate、expected result、
執行能力、期限、nonce 及必要證據；成功狀態與 receipt 同交易。
預覽保存可安全顯示的確切新內容；持久 receipt 不複製原文。
以 stable ID 與 revision 對應歷史，不以「後端說成功」自證。
對執行後 readback 的讀取授權須一併涵蓋。

新 `erase-content` 需要獨立精確的清除權限與狀態證據，
不能要求禁止保存的記憶重新通過「可新增」eligibility。
它不採納該內容為可信資訊，也不繞過身份、範圍、結構與能力檢查。
遇到不能精確定位的損毀檔仍拒絕，沒有通用破壞性修復路徑。

無原文的 receipt 仍可能有身份或內容雜湊的推知風險；不得宣稱匿名。
不透明 operation ID 優先，保留的證據引用限本機且有獨立讀取權限。
已刪正文不因 proof 永存而留在 old/new value 或 diff。

G0 須固定 receipt／delete marker 的保留窗口，以及 durable acceptance epoch／
時間下限：裁剪舊防重放資料前先持久提升拒絕下限，所有較早授權一律拒絕；
重新新增必須用新的明確授權與新 identity。
不能在移除 idempotency row 後把原請求當首次執行。
時間不可驗證時不裁剪。防重放窗口及證據保留要求衝突時，保留拒絕狀態，
不得藉此無限增加全文。此機制也需要新 contract，不能改寫舊 receipt。

### 清除、實體殘留與壓縮的成功邊界

內容列／版本／索引的 SQL 移除與 receipt 原子提交後，回報
`content-removed`；受管理檔案殘留尚未清除則回報 `sanitization-pending`。
內容與受管理殘留清除通過後，`erase-content` 即可完成。
未要求 `compact` 時，另報「內容刪除完成；磁碟空間尚未回收／可再利用」，
不因此把內容刪除列為 pending。只有當次授權也包含空間回收，才使用
`space-reclaim-pending`，並以所有獲准階段完成判定整體請求完成。
跨步驟不能宣稱符合舊 M0 單一 applied receipt 的整體成功語意。

清除預覽須列受管理主檔、FTS shadow data、journal/WAL、temp 等適用對象，
以及已知非受控副本。若必要的殘留清除涉及資料庫級維護，預覽須揭露影響，
並取得對應權限，不能由單筆刪除權限自行推定。G2 須在選定的 SQLite journal mode 上資格驗證
checkpoint／受控檔案整理／VACUUM 或等效程序，而非機械串接所有命令。
[SQLite 的 secure_delete 限制](https://www.sqlite.org/pragma.html#pragma_secure_delete)
說明單一 pragma 不能保證清掉 FTS shadow table 殘留。

為避免清除後舊資料再匯入，pending 狀態由受控操作紀錄保存；明確重試或重開
管理核心只做狀態驗證，需有效原授權或新確認才執行剩餘維護。
不啟動 daemon，不在開庫時偷偷清理，也不把不確定 commit 當作成功。

`compact` 影響資料庫檔案全體布局，須有精確資料庫級維護權限；
單筆刪除權限不會自動授權跨 principal 的檔案重整。
首版使用單一核准 principal/root 的 envelope；共用庫不在資格範圍。

空間／完整性不足時保留可判讀的階段結果，不以還原舊副本恢復已刪內容。
受管理檔案回收不證明 SSD、外部備份及快照的取證級抹除。
任何這類強保證須另有 storage/security design。
